Certificates, CSRs, and Keys

A lot of TLS confusion vanishes when you separate three objects: the private key you keep secret, the CSR you send to a CA, and the certificate you get back.

The roles

  • Private key: proves ownership, stays secret, signs things.
  • Public key: goes in the cert and can be shared freely.
  • CSR: a signed request asking for a certificate to be issued.
  • Certificate: a CA-signed identity binding for the public key.

The certificate profile is defined in RFC 5280; the CSR format is defined in RFC 2986.

What the CA is actually signing

The CA is not signing your private key. It is signing a statement that says, in effect, “this public key belongs to this subject, for this purpose, for this period of time.”

That statement is what clients later validate through a chain of trust.

The chain validation rules come from RFC 5280.

What lives in a certificate

At minimum, a certificate includes a subject, issuer, public key, serial number, validity period, signature algorithm, and extensions. The extensions are where practical behavior often lives: subject alternative names, key usage, and extended key usage are the fields that decide whether the certificate is usable for a given purpose.

Why the CSR matters

The CSR is how you ask for issuance while keeping the private key private. The request is signed with the private key, which proves that the requester actually controls the key pair associated with the public key in the request.

OpenSSL’s req tool documents the -new, -newkey, -key, -text, and -verify options for this workflow.

Practical flow

# 1. Create a key and CSR
openssl req -new -newkey rsa:2048 -nodes -keyout key.pem -out request.csr

# 2. Inspect the CSR
openssl req -in request.csr -noout -text -verify

# 3. Inspect a certificate
openssl x509 -in cert.pem -noout -text

How to read the output

  • Subject tells you who the cert claims to represent.
  • Issuer tells you which CA signed it.
  • Public key shows the shareable half of the key pair.
  • Validity dates tell you whether the cert is currently usable.
  • Extensions tell you what the cert is allowed to do.

Useful OpenSSL commands

# Show a live server's chain
openssl s_client -connect example.com:443 -servername example.com -showcerts

# Inspect a certificate request
openssl req -in request.csr -noout -text -verify

# Print certificate details
openssl x509 -in cert.pem -noout -text

# Create a quick test self-signed cert
openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem

OpenSSL documentation for these commands is in openssl-req, openssl-x509, and openssl-s_client.

Check yourself

  • Which artifact do you keep secret?
  • Which artifact do you send to the CA?
  • What does the CA sign?
