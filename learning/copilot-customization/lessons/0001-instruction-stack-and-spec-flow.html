Lesson 1 · Practical workflow

Use the Instruction Stack Without Bloating Context

The best Copilot setup is usually not “more context.” It is “the right context in the right layer.” Stable project knowledge goes into instructions, repeatable tasks go into prompt files, and one-off work stays in the prompt.

Layer 1: personal instructions

Use these for standing preferences that should follow you everywhere you use Copilot. Keep them short and boring: language, tone, formatting style, and a few habits that never change.

  • Preferred language
  • Output style
  • Level of detail
  • Formatting preferences

GitHub Docs says personal instructions apply to every conversation on GitHub and have the highest priority.

Layer 2: repository instructions

Use these for things Copilot should know about the repo itself: build steps, test commands, directory layout, naming, architecture invariants, and other durable rules.

  • Repo-wide conventions
  • Path-specific rules for one area
  • Commands Copilot should run or respect
  • Definitions and invariants

GitHub Docs describes repository instructions as repository-specific guidance and notes that path-specific instructions can apply only where relevant. It also says repository instructions must be no longer than 2 pages and must not be task specific.

Layer 3: prompt files

Use prompt files for repeated tasks. That is the sweet spot for things like explaining code, drafting tests, writing a PR summary, or generating onboarding docs. They give you a reusable ask without turning your repo instructions into a dumping ground.

GitHub Docs says prompt files are reusable prompts for specific tasks and are available in VS Code, Visual Studio, and JetBrains IDEs.

The flow that usually works best

  1. Write a short user story.
  2. Add acceptance criteria.
  3. Add only durable repo knowledge to instructions.
  4. Use a prompt file or direct prompt for the task.
  5. Ask for a plan when the task is not trivial.
  6. Implement one small change, then validate it.

User story to spec

Story
As a developer, I want Copilot to understand our build and test conventions so that it can suggest changes that pass the first review.

Acceptance criteria
- Copilot knows the correct build command
- Copilot knows the test command for this repo
- Copilot respects our naming and folder conventions
- Copilot does not get one-off task details from instructions

Spec note
- Keep repo instructions under 2 pages
- Put repeatable tasks into prompt files
- Keep temporary implementation details in the issue or PR

What to avoid

  • Long instructions that repeat the README
  • Conflicting instructions for the same behavior
  • One-off feature details promoted into repo instructions
  • Examples that are so broad they stop being useful

Why this helps

GitHub's docs and the Copilot customization library point toward the same pattern: use small, layered customizations rather than one giant prompt blob. The research on prompt influence also suggests that a clear purpose statement and concrete examples can improve output, but only when they are narrowly relevant. In other words, clarity helps more than volume.

Quick exercise

  1. Take one real task you are about to ask Copilot to do.
  2. Write a three-line user story and three acceptance criteria.
  3. Decide which facts belong in instructions and which belong only in the prompt.
  4. Trim anything that is temporary, redundant, or conflicting.
