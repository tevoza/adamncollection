# Writing a post for adamncollection

This repo is a hand-rolled Hugo blog. Posts here are technical explainers (software, architecture, .NET, databases, security) written by Claude and stamped as AI-generated by the site itself. The user cares most about two things: **the concepts are technically right**, and **the prose is concise**. Word count is never a goal.

Read `AGENTS.md` first if you haven't this session; its invariants (no theme, content under `content/<section>/`, never flip `draft`) apply throughout.

There are two modes. A **new post** follows sections 1–8 in order. **Revising an existing post** starts with the section below, then reuses sections 3–8.

## Revising an existing post

The user's "pattern" is everything in sections 2–5 below: front matter conventions, concise style, sourced claims, diagrams where they help. The reference example is `content/software/code-smells-and-the-patterns-that-fix-them/`; use it for voice comparison. Older posts predate some of the pattern. Start by finding out where this post stands, rather than editing straight away.

1. **Read the post and its bundle in full**, plus the user's extra instructions for this revision (a new section, a different angle, "tighten it", "add diagrams", a correction). Treat those instructions as the priority: the alignment work serves them, not the other way round.
2. **Review it against the pattern.** Note concretely, by section:
   - **Style:** padding, restated sentences, caveats that have grown into their own paragraphs, and an in-body "this post is AI-written" paragraph (remove it; the site banner covers that).
   - **Sourcing:** specific claims without a footnote, footnotes that don't support their sentence, unused or undefined footnotes. Run `scripts/check_post.py` for the mechanical part.
   - **Structure:** does it work from something the reader recognises toward the concept? Is there a running example, and is it consistent?
   - **Diagrams:** places where a picture would explain a mechanism better than the prose, and existing diagrams that don't match the palette or overflow.
   - **Accuracy:** anything that looks wrong or outdated. Spot-check suspicious or version-sensitive claims at this stage. Fully re-verifying every footnote on a long post isn't worth it here; that happens for claims you change or add, in step 5.

   Group the findings by these headings, with a line reference and a few words each. The user wants to scan them, not read an essay.
3. **Interpret the extra instructions against that review.** Say how you read them, especially if they're brief ("make it like the code smells one" means structure and style, not content). Where they conflict with the pattern, the instructions win. For "tighter", give a rough expected reduction (e.g. "about 25–30% of prose words"). That's an estimate of what the cuts will yield, not a target.
4. **Propose a short plan:** what you'll change, what you'll leave, and anything that needs the user's call (cutting a section, changing the angle). If the post is `draft: false`, say plainly that it's live and pushing the revision changes the public page. Get a go-ahead before large rewrites. Small mechanical fixes don't need one.
5. **Apply it**, keeping every code sample, diagram and sourced claim unless the plan says otherwise. Verify any claim whose wording you change or that you add. Then run the build check (section 6). For substantial revisions, do one independent review round (section 7). For light tightening, your own pass is enough. Say which you did.
6. **Report** what changed and the before/after prose word count (the check script prints it), so the user can see how much tighter the post is.

Don't touch `draft`, the date or the slug unless asked. Changing the slug breaks links and `relref`s from other posts.

## 1. Plan before writing

Settle these with the user if they aren't clear from the request — they change the whole post:

- **Scope** — one post or a series. Default to one post unless the topic plainly splits.
- **Angle** — the organising idea. The best posts here start from something the reader recognises (a smell, a failure, a workload, a question) and work toward the concept, rather than reciting a catalogue.
- **Examples** — one running example (usually a C#/.NET payments or backend codebase, matching the user's background) beats unrelated snippets per section. Keep type and member names consistent across sections; reviewers check this.

Look at one or two sibling posts in the same section for structure and tone, and note posts worth cross-linking with `{{< relref "file.md" >}}`.

## 2. Files and front matter

Create a page bundle: `content/<section>/<slug>/index.md`, with diagrams beside it. The slug is the title in kebab case.

```yaml
---
title: "Title Case Name"
date: <today, ISO 8601 with +02:00>
draft: true
tags: ["<section>", "<topic>", ..., "ai-generated"]
description: "One sentence: what the reader will understand by the end."
---
```

- `draft: true` always. Publishing is the user's decision; never flip it unless they ask.
- The `ai-generated` tag is what renders the disclosure banner (`layouts/_default/single.html`). Because the site already says it, **don't** add an in-body paragraph about the post being AI-written or about the footnoting policy — the user called that fluff.

## 3. Style

- **Concise and clean.** Shortest wording that keeps the technical point. One idea per paragraph. Don't restate the previous sentence. Keep "when not to" counterweights to a sentence or two.
- When review feedback adds a caveat, fold it into a clause where it belongs — don't give it its own paragraph. Accumulated caveats are the main way these posts bloat.
- Code samples carry a lot of the explanation; keep them, keep them compiling (allowing `...` bodies), and let prose point at what matters in them.
- Bold lead-ins (`**The smell.**`, `**Why it hurts.**`) work well for repeated section shapes. `##`/`###` headings, ```` ```csharp ```` fences.
- End with something useful to scan — a cheat sheet table or short "what to take from this" — when the post covers many items.

## 4. Sourcing

Specific claims — quotes, what an author said, API behaviour, version numbers, limits — get a `[^name]` footnote to a primary source (vendor docs, the original paper or book, the author's own post). Verify each with WebFetch before citing; don't cite from memory when the page is reachable. Reasoning built on top of sources should read as reasoning, uncited. Footnote definitions go at the very end, one line each: `[^name]: Author, ["Title"](url) — what it supports.`

Every footnote definition must be referenced, and every reference defined; `scripts/check_post.py` checks this.

## 5. Diagrams

The user likes SVG diagrams — use one wherever a picture shows a mechanism better than prose (before/after refactors, boundaries, state machines, layering, request flow). Read `references/svg-diagrams.md` before drawing: it has the site palette, a template, and the text-fit arithmetic that stops labels overflowing boxes. Reference them as `![descriptive alt text](name.svg)`, with alt text that describes what the drawing actually shows.

## 6. Build check

Run `python .claude/skills/write-blog-post/scripts/check_post.py content/<section>/<slug>` from the repo root. It builds the site with drafts into a temp folder (finding Hugo even when it isn't on PATH), checks footnotes and image links, flags diagram text under 12px or colours outside the palette, and prints prose word counts per `##` section (useful for deciding where to cut). Fix anything it reports as a problem; colour warnings may be deliberate.

For the user to preview, start `hugo server -D` in the background and give them the post URL (the site lives under `/adamncollection/`; the port is printed on startup).

## 7. Independent review rounds

A new post gets two rounds; a substantial revision gets one (the first). After the draft:

1. **Review 1** — spawn a fresh general-purpose agent with the brief in `references/review-brief.md`. Apply what holds up; verify contested claims yourself before changing or rejecting them.
2. **Final review** — a second fresh agent, same brief plus "check that the review-1 fixes landed without regressions."
3. Tell the user what each round raised, what changed, and what was declined and why — briefly.

If you add a section after a review has started, the reviewer won't have seen it; check those sections yourself before calling the post done and say so.

## 8. Finishing

Don't commit or push unless asked. When asked: one commit per post, message `Add a draft post on <topic>` with a short body of what it covers, ending with the attribution line the session provides. The repo deploys from `main`; a `draft: true` post won't appear on the live site, so tell the user that when pushing.
